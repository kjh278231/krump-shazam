# 설계안 B — 음악 파운데이션 모델 기반 핑거프린트 (MuQ, Singh et al. 2025)

작성 2026-10-13 · 상태: 제안

근거 논문: Singh et al., *Robust Neural Audio Fingerprinting using Music Foundation Models*
([arXiv 2511.05399](https://arxiv.org/abs/2511.05399), NeurIPS 2025 워크숍).
백본은 [tencent-ailab/MuQ](https://github.com/tencent-ailab/MuQ)입니다. **논문 코드는 공개되지 않았습니다.**
이 설계는 논문에 적힌 구성을 직접 구현하는 것을 전제로 합니다.

## 1. 왜 바꾸는가

[평가](evaluation.md) "실제 영상 테스트"에 정리된 대로, 배틀 영상에서 Panako가 실패하는 원인은 **홀 잔향 + 관중 + MC로
스펙트럼 피크가 번지는 것**입니다.

- 라벨된 실패 3건(DARK, KILL EM, Afro Krump)은 모두 라이브러리에 있고 속도 1.000이었습니다.
- 합성 `crowd0_room`은 0%이고, 리듬 fallback은 71%를 맞히지만 unknown 곡의 15%에도 후보를 내서 추가 확인
  전용입니다.

설계안 A(NMFP)는 작은 CNN을 열화 데이터로 학습합니다. 이 안은 **대규모 음악 데이터로 사전학습된
3억 파라미터 모델(MuQ)의 표현**을 백본으로 쓰고, 그 위에 핑거프린트 헤드를 대조학습으로 얹습니다.

논문 결과(5,000곡, 10 s 쿼리, 여러 열화 평균 top-1):

| 모델 | top-1 |
|---|---|
| MuQ 미세조정 | 88.2% |
| MuQ 고정(frozen) | 83.9% |
| GraFPrint | 67.8% |
| NAFP | 63.5% |
| Dejavu (Shazam식 피크 해시) | 49.2% |

특히 코덱 압축(MuQ 96 vs NAFP 10)과 대역통과(63 vs 18)에서 차이가 큽니다. 다만 논문이 잔향만 따로
떼어 수치를 내지 않았고, 실제 공연장 녹음 평가도 없습니다. **우리 실패 조건에서 통할지는 Phase 0에서
직접 확인해야 합니다.**

## 2. 목표와 비목표

**목표**
- 잔향 + 관중 조건에서 확정 수준 정밀도로 식별합니다. 1차 목표는 리듬 fallback의 top-1 71%를 넘으면서
  holdout 오확정 0건입니다.
- 라벨된 실제 배틀 실패 3건을 맞힙니다.
- 깨끗한 업로드 100%, 속도 ±3%, 오확정 0건은 유지합니다.

**비목표**
- 비슷한 곡 찾기. 파운데이션 모델은 장르나 분위기 같은 의미 정보를 많이 담고 있어서, 이 안의 핵심 위험이
  바로 "비슷한 크럼프 곡을 같은 곡으로 판정하는 것"입니다(§7). 목표는 계속 option B, 즉 같은 녹음
  식별입니다.
- Panako 제거.

## 3. 바뀐 구조

```
                ┌────────────── server/app.py (Windows, :8765) ───────────────┐
 extension ──▶  │ ffmpeg → 22.05 kHz WAV (Panako)  /  24 kHz (MuQ)             │
 (30 s Opus)    │   ├─▶ Panako query (기존)                                    │
                │   └─▶ MuQ: 5 s 창 → 백본(GPU) → MLP 헤드 → 256-d              │
                │          → 최근접 검색 → 시간축 정렬(Hough/Huber)              │
                │ grouping.group / verdict (점수 체계별 임계값)                   │
                │ 둘 다 실패 → rhythm fallback (기존, 추가 확인 전용)              │
                └──────────────────────────────────────────────────────────────┘
 학습과 서빙 모두 Windows 네이티브 PyTorch (CUDA), RTX 4070 Ti 12 GB
```

**결정 1: Panako와 병렬로 실행하고 판정을 합칩니다.** 규칙은 설계안 A와 같습니다.
- Panako 확정 + MuQ가 다른 곡 → 추가 확인
- Panako 실패 + MuQ 확정 → 확정(`method=neural`)
- 둘 다 실패 → rhythm

**결정 2: 전부 Windows 네이티브로 갑니다.** MuQ는 PyTorch이고 `pip install muq`로 설치합니다(코드 MIT).
설계안 A와 달리 WSL2나 ONNX 변환이 필요 없습니다. 서버 프로세스가 모델을 GPU에 상주시킵니다.
fp32 기준 가중치 약 1.2 GB이고, README는 NaN 문제 때문에 fp32 추론을 권장합니다.

**결정 3: 세그먼트는 5 s로 합니다. 논문은 10 s입니다.**
- 10 s는 DJ 점프(WWB 9에서 확인)나 partial 확인처럼 짧은 쿼리에 불리하고, 위치를 찾는 정밀도도 떨어집니다.
- 라이브러리는 5 s 창 / hop 2.5 s, 쿼리는 5 s 창 / hop 0.5 s로 처리합니다.
- 2.5 s와 10 s도 Phase 0에서 함께 비교합니다. 2026년 *Segment Length Matters* 연구는 짧은 세그먼트가
  대체로 유리하다고 보고했지만, 큰 백본에서는 다를 수 있습니다.

**결정 4: 검색은 numpy 전수 검색입니다.**
- 244 h ÷ 2.5 s ≈ 35만 세그먼트 × 256차원 = fp16 약 180 MB입니다.
- 쿼리 51창이면 CPU로 수십 ms입니다. FAISS가 필요 없습니다.

## 4. 구성 요소

### 4.1 모델
| 항목 | 값 | 출처 |
|---|---|---|
| 백본 | `OpenMuQ/MuQ-large-msd-iter`, 약 3억 파라미터, **입력 24 kHz 필수** | MuQ README |
| 백본 출력 | 1024-d 프레임 특징 (프레임 레이트는 확인 필요, 약 25 Hz 예상) | 논문: 1024-d |
| 레이어 | 논문 미기재 → Phase 0에서 레이어별 비교, 학습 가능한 가중합도 후보 | — |
| 풀링 | 프레임 평균 (대안: attention pooling) | — |
| 헤드 | 1024 → 4096 (ELU) → 256, L2 정규화 | 논문 (선형보다 우수) |
| 손실 | 대조 손실 (NT-Xent, 원본 vs 증강 쌍) | 논문 (세부 미기재) |
| 학습률 | 3e-5 (MuQ 미세조정) | 논문 |

**라이선스:** MuQ 가중치는 **CC-BY-NC 4.0**입니다. 개인 비상업 사용은 괜찮지만 상업적 사용은 할 수
없습니다.

### 4.2 증강 파이프라인
논문 증강(시간 늘이기 0.7–1.5, 피치 ±5, MUSAN 소음, Aachen RIR, 대역 필터, 에코, Encodec)에서 시작해서
우리 실패 조건 쪽으로 비중을 옮깁니다.

| 열화 | 범위/소스 | 메모 |
|---|---|---|
| 큰 홀 잔향 | OpenAIR 대형 공간, MIT IR, Aachen AIR, DRR −10 ~ +3 dB | 진단상 핵심 약점 |
| 관중 | FSD50K Crowd/Cheering/Applause + `make_testset.crowd()` | — |
| MC 음성 | LibriSpeech/MUSAN → PA 시뮬레이션(대역 제한, 클리핑, IR) | — |
| SNR | −3 ~ +10 dB | — |
| 속도 | **0.9–1.1 리샘플** (템포와 피치 같이) | DJ 피치 페이더. 논문의 0.7–1.5는 우리 용도에 과함 |
| 저역 손실 | 고역통과 100–300 Hz | — |
| 코덱 | AAC → Opus 재인코딩 | YouTube → 탭 캡처 경로 |
| 대역/에코/Encodec | 논문 값 그대로, 낮은 확률로 | 일반 강건성 |

증강 코드는 `poc/augment.py` 하나로 모으고 `make_testset.py`와 같이 씁니다. 그래야 평가 조건과 학습 조건이
어긋나지 않습니다. 단, 평가에 쓰는 IR과 소음 파일은 학습에서 빼서 따로 둡니다.

### 4.3 학습 데이터 분할
설계안 A와 같습니다.

| 그룹 | 비율 | 학습 | 인덱스 | 용도 |
|---|---|---|---|---|
| train | ~88% | ✔ | ✔ | 학습 |
| index-only | ~10% | ✘ | ✔ | 새로 추가할 곡에 대한 일반화 측정 |
| holdout | `db/holdout.txt` (109 파일) | ✘ | ✘ | 오탐 측정 |

- `same_audio.csv` 링크와 content id로 같은 녹음을 묶고, 대조 손실에서 서로 negative가 되지 않게 마스킹합니다.
- **같은 앨범, 같은 프로듀서의 다른 곡을 같은 배치에 일부러 넣습니다**(hard negative). 파운데이션 모델은
  이런 곡들을 원래 가깝게 놓기 때문에, 이 학습이 "비슷한 곡 ≠ 같은 곡"을 가르치는 핵심입니다.
- 외부 데이터(FMA 등)를 섞을지는 Phase 1 결과를 보고 정합니다. 논문은 Disco-10M에서 30만 샘플을 썼습니다.

### 4.4 검색과 정렬
1. 쿼리 → 24 kHz → 5 s 창(hop 0.5 s) → 256-d.
2. 창마다 top-k(=10) 이웃 `(track_id, t_ref, sim)`을 찾고, sim < τ(논문 0.7, 보정 대상)는 버립니다.
3. `track_id`별로 `t_ref ≈ a·t_query + b`를 맞춥니다.
   - a는 0.90–1.10을 0.01 간격으로 훑는 Hough 투표로 고르고, 그 뒤 Huber 회귀로 다듬습니다.
     논문은 Huber 회귀를 여러 시드로 돌렸습니다.
   - 이것은 Panako 패치 1번(강건 정렬)과 같은 발상입니다.
4. 점수 = inlier 수 × 평균 유사도. 결과를 `common.Match`로 바꿉니다.
   - `time_factor` = a × 100
   - `match_start` = 첫 inlier의 `t_ref`
5. `grouping.group()`을 그대로 쓰고, 임계값은 점수 체계별 묶음으로 따로 보정합니다(§6).

## 5. 구현 단계

### Phase 0 — 백본 영점 평가 (학습 없음)
공개된 핑거프린트 헤드가 없으므로, **헤드 없이 백본 임베딩만으로** 잔향에 버티는지 먼저 봅니다.
1. Python 3.12 환경에 `torch`(CUDA)와 `muq`를 설치합니다. 3.12에서 안 되면 별도 venv를 씁니다.
2. `poc/fm_probe.py`: 합성 세트의 일부(`clean`, `crowd3`, `crowd0_room`, `room_drr−3`, 각 100클립)와
   해당 원곡 구간에서 레이어별 평균 풀링 임베딩을 뽑습니다.
3. 레이어별로 "열화 클립 ↔ 원곡 같은 위치" 코사인 순위를 매깁니다. 비교 대상은 라이브러리 무작위
   세그먼트 1만 개입니다.
4. 처리 속도를 측정합니다(창/초, VRAM). 이 값으로 전체 인덱싱 시간을 추정합니다.
   - 거친 계산: 35만 창 × 5 s ≈ 프레임 4,400만 개, 프레임당 약 0.6 GFLOP이면 2.6e16 FLOP입니다.
     fp32 실효 15 TFLOPS 가정 시 약 30분이고, 디코딩까지 합쳐 1–2시간으로 예상합니다.

**결정 기준:** 헤드 없이도 `crowd0_room`에서 정답 위치가 top-10 안에 자주(≥ 30%) 들어오면, 백본에
정보가 남아 있다는 뜻이므로 Phase 1로 갑니다. 거의 없으면 이 안은 중단하고 설계안 A에 집중합니다.

### Phase 1 — 백본 고정 + 헤드 학습 (임베딩 캐시)
백본을 고정하면 **증강한 오디오의 백본 출력을 미리 계산해 둘 수 있습니다**. 그러면 헤드 학습은 캐시된
벡터만으로 몇 분이면 끝납니다.
1. `poc/fm_cache.py`
   - train 그룹 곡마다 5 s 세그먼트 약 20개를 뽑습니다.
   - 세그먼트마다 원본 1개 + 증강 4개를 만듭니다(§4.2).
   - Phase 0에서 고른 레이어 몇 개의 평균 풀링 출력을 fp16으로 저장합니다.
   - 규모: 4,000곡 × 20 × 5 ≈ 40만 개 → 레이어 4개 × 1024 × fp16 ≈ 3.3 GB. 예상 소요 1시간 안팎입니다.
2. `poc/fm_train_head.py`
   - NT-Xent(온도 보정) + 같은 녹음 마스킹 + 같은 앨범 hard negative.
   - 배치 4,096도 VRAM에 쉽게 들어갑니다(벡터만 쓰므로).
   - 레이어 가중합 vs 단일 레이어도 비교합니다.
3. `poc/build_fm_index.py`: 라이브러리 → `db/fm/emb.f16.npy`, `segments.npy`. 재시작 가능해야 합니다.
4. §6 평가.

한계: 증강 view가 캐시 시점의 4개로 고정됩니다. epoch마다 새 증강을 볼 수 없어서 다양성이 줄어듭니다.
과적합이 보이면 캐시를 다시 만들거나 view 수를 늘립니다.

### Phase 2 — 백본 부분 미세조정 (선택)
논문에서 고정 → 미세조정 차이는 4.3포인트(83.9 → 88.2)였습니다. Phase 1이 목표에 못 미칠 때만 합니다.
- 상위 N개 레이어만 풀거나 LoRA를 쓰고, gradient checkpointing을 켭니다. 12 GB 제약 때문입니다.
- 12 GB에서는 배치가 작아 대조 손실의 negative가 부족합니다. MoCo 큐나 cross-batch memory로
  negative 수만 개를 확보합니다.
- 증강은 온라인으로 적용합니다(캐시 없음). 학습 시간은 수십 시간 단위로 예상되므로, 체크포인트마다
  평가해서 조기 종료합니다.

### Phase 3 — 서버 통합
1. `server/app.py`: 시작할 때 MuQ와 헤드를 GPU에 로드합니다(약 1.5 GB VRAM). 임베딩 행렬도 로드합니다.
   `/identify`에서 ffmpeg 24 kHz 변환을 추가하고, Panako와 병렬로 돌린 뒤 판정을 합칩니다.
   - 예상 쿼리 시간: 51창 GPU 추론 0.3–1 s(Phase 0에서 측정).
   - GPU가 없거나 다른 프로그램이 점유 중일 때의 CPU fallback은 너무 느릴 수 있습니다(수 초–수십 초).
     이때는 MuQ를 건너뛰고 기존 흐름(Panako → rhythm)으로 갑니다.
2. 팝업에 `method=neural`과 추정 속도(a)를 표시합니다.
3. README에 음악 추가 시 `build_fm_index.py` 재실행 안내를 넣습니다.

## 6. 평가 계획

설계안 A와 같은 세트를 써서 두 안을 직접 비교할 수 있게 합니다.

| 세트 | 내용 | 지표 |
|---|---|---|
| 합성 | `poc/testset` 6개 조건 + `poc/diag` 잔향/관중 진단 조건 | top-1, 확정 비율, 오확정 |
| index-only | 학습에 안 쓴 곡 | 학습곡과의 차이 |
| holdout | 109 파일 | 오확정 (목표 0) |
| 실제 | 라벨된 배틀 윈도우, `recordings/log.csv` ✔/✘ | 확정/추가 확인/실패 |
| **유사곡 혼동** | 같은 앨범·프로듀서·`same_audio` 아닌 공유 루프 곡이 1위나 경쟁자로 나온 횟수 | 이 안의 핵심 위험 지표 |

**선행 작업:** 실제 실패 라벨이 3곡뿐입니다. `realtest/labels.csv`를 만들고, [평가](evaluation.md) "미확인 후보"의 리듬 후보를
확인하고, 확장 프로그램 피드백을 쌓아서 실제 세트를 늘립니다.

비교 기준선: Panako, rhythm, 현재 운영 구조(Panako + rhythm), 그리고 설계안 A를 진행했다면 NMFP.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| **비슷한 크럼프 곡을 같은 곡으로 판정** (의미 표현이라서) | 같은 앨범/프로듀서 hard negative 학습, 시간축 정렬 inlier 하한, 유사곡 혼동 지표로 임계값 보정 |
| 논문 코드 미공개 → 재현 실패 | Phase 0/1을 작게 시작. 세부(온도, 레이어)는 실험으로 정함 |
| 잔향 성능이 논문에 따로 없음 | Phase 0 결정 기준으로 조기 중단 |
| 12 GB VRAM으로 미세조정이 빠듯함 | Phase 1(고정 + 캐시)을 기본으로. Phase 2는 LoRA + checkpointing + MoCo 큐 |
| 쿼리 지연, GPU 의존 | 모델 상주, 창 수 조절, GPU 불가 시 기존 흐름으로 우회 |
| fp16에서 NaN | MuQ 권장대로 fp32 추론. 학습은 AMP 쓰되 백본은 fp32 유지 |
| CC-BY-NC 가중치 | 개인 비상업 사용으로 한정 |
| Python 3.12 호환성 | 안 되면 별도 venv. 서버도 그 환경에서 실행 |

## 9. 설계안 A와 비교

| | A: NMFP | B: MuQ |
|---|---|---|
| 실제 공연장 평가 근거 | 있음 (실환경 10 s 84.6%) | 없음 |
| 사전학습 핑거프린트 가중치 | 있음 → 바로 영점 평가 가능 | 없음 → 헤드 학습 필요 |
| 모델 크기, 쿼리 비용 | 작은 CNN, CPU로 충분 | 3억 파라미터, GPU 사실상 필수 |
| 환경 | 학습은 WSL2(TF), 서빙은 ONNX | Windows PyTorch 하나 |
| 템포 강건성 | 없음 (Panako가 담당) | 증강으로 일부 확보 |
| 유사곡 오판 위험 | 낮음 | **높음** (의미 표현) |
| 라이선스 | AGPL-3.0 | CC-BY-NC 4.0 |

권장 순서: **A의 Phase 0을 먼저 합니다.** 사전학습 가중치가 있어서 가장 싸게 신호를 얻을 수 있습니다.
B의 Phase 0(백본 probe)은 A와 독립적이라 병행할 수 있습니다.
