## 0. 요약

1. **대화의 원리 설명은 원 논문과 맞습니다.** 내용은 피크 constellation → 두 피크 조합 해시 → Δt 히스토그램
   투표, 32비트 해시, 1–2% 생존으로도 식별, 펍 소음 실험(10,000곡, 250샘플, 8 kHz)입니다. 숫자와 수식은
   대부분 논문 그대로입니다.
2. **fan-out 해석은 바로잡아야 합니다.** fan-out은 생존 확률을 피크 하나의 생존 확률 p보다 "높이지"
   않습니다. 피크를 짝지으면서 p²로 떨어진 생존 확률을 거의 p까지 **되돌릴** 뿐입니다(논문 2.2절).
3. **대화는 잡음을 더하기 모델(x = s + n)로만 다룹니다. 우리 실패 원인은 잔향입니다.** 잔향은 컨볼루션
   열화입니다. 원 논문도 잔향은 실험하지 않았고, 라이브 녹음으로 일반화되리라 기대하지 않는다고 적었습니다
   (3.3절).
4. **우리 엔진(Panako)은 Shazam식 2점 해시가 아닙니다.** 3점(triplet) 해시이고, 해시에 피크 **크기 순서
   비트**가 들어갑니다. 같은 피크 생존 확률에서 해시 생존은 p³이고, 진폭이 바뀌면 비트가 뒤집힐 수
   있습니다. 이것이 속도·피치 불변성의 대가입니다. 우리 crowd-only 성적이 Shazam 논문보다 약한 이유의
   후보입니다(가설).
5. 이 검토에서 나온 **개선 후보 E1–E6**은 5장에 있습니다. 앞쪽 두 개(E1, E2)는 fingerprint DB를 다시
   만들지 않고 측정부터 할 수 있습니다.

## 1. 대화 내용 정리

### 1.1 첫 질문 — "샤잠은 어떻게 그렇게 빨리 찾나"

대화가 설명한 4단계입니다.

1. **스펙트로그램 → 국소 피크.** STFT 후 주변보다 에너지가 큰 점만 남깁니다(constellation map).
   진폭은 버리고 (시간, 주파수)만 씁니다.
2. **두 피크 → 해시.** `hash(f1, f2, Δt)`로 만들고 절대 시각은 해시에 넣지 않습니다(어느 구간을 녹음해도
   같은 해시). 32비트 정수로 압축합니다.
3. **역색인.** `hash → [(곡 ID, 곡 내 시각), …]`. 쿼리 해시가 나온 곡만 조회합니다.
4. **Δt 투표.** `Δt = t_원곡 − t_녹음`을 곡별로 히스토그램으로 만듭니다. 한 Δt에 표가 몰리면 정답입니다.
   우연히 같은 해시는 Δt가 흩어집니다.

이어서 대화는 이 프로젝트에 맞춘 구조(STFT → 피크 → pair hash → SQLite/LMDB 역색인 → 5–10초 쿼리)를
추천했습니다. 0.95배속이나 피치 변경은 "기본 방식에 추가 처리가 필요하다"고 했습니다. SoundHound의
허밍 검색은 멜로디 비교라 다른 문제라고 덧붙였습니다.

### 1.2 둘째 질문 — "박수와 함성이 섞여도 어떻게 찾나"를 더 자세히

| 주제 | 대화 내용 |
|---|---|
| 신호 모델 | `x(t) = s(t) + n(t)`. STFT는 선형이라 복소 스펙트럼도 `X = S + N`. 음악과 잡음이 시간·주파수를 모두 겹쳐 차지하지는 않아서, 강한 음악 피크는 살아남습니다. 위상 간섭으로 약해지거나 잡음 피크에 가려질 수도 있다고 단서를 달았습니다. |
| 진폭 제거 | 해시에 진폭이 없어서 음량, 녹음 레벨, 완만한 EQ 변화에 둔감합니다. |
| 잡음 유형 | 박수는 짧고 넓은 대역이라 순간적으로 가립니다. 함성·대화는 기본음과 배음이 움직이며 일부 피크를 가립니다. 지속 소음은 대비를 낮춥니다. 다른 음악은 그 곡의 지문도 같이 나옵니다. 박수 구간 앞뒤의 지문은 살아남습니다. |
| fan-out | 기준 피크(anchor) 하나를 target zone의 F개 피크와 짝짓습니다. 쌍 하나의 생존은 `p²`, anchor당 하나 이상 생존은 `p·[1 − (1 − p)^F]`. 예: p = 0.2, F = 10이면 4.0%와 17.9%. 독립 가정은 박수처럼 동시에 여러 피크를 지우는 잡음에서 깨진다고 했습니다. |
| 가짜 해시 | 잡음이 만든 해시는 원곡 해시와 충돌해도 일관된 Δt를 만들지 못해서 투표에서 걸러집니다. 몇 표가 필요한지는 DB 크기, 충돌률, 허용 오탐률에 달렸습니다. |
| 1–2% | 심하게 오염된 15초 샘플에서 해시의 1–2%만 살아남아도 유의미하게 식별한 사례가 있습니다. |
| 실험 | 10,000곡 DB, 250샘플, 펍 소음, 5/10/15초, 8 kHz 모노. 발표 슬라이드 그래프를 읽은 근삿값 표를 냈습니다(아래 2장). GSM 코덱을 더하면 크게 나빠집니다. |
| 실패 상황 | 계속되는 큰 박수, 음악보다 훨씬 큰 소음, 0.95배속, 피치 변경, 라이브·커버. |
| 추천 순서 | ① 8–10초 기본 검색 → ② 실패 시 15–20초나 다른 구간 → ③ 정렬 해시 수와 2위와의 차이로 신뢰도 → ④ 속도·피치는 별도 알고리즘 → ⑤ 그다음에 Demucs 같은 분리로 A/B. 분리가 드럼 어택이나 배음을 망가뜨려 오히려 나빠질 수 있다고 경고했습니다. 참고 구현으로 audfprint와 Panako를 들었습니다. |

결론 문장은 이렇습니다. 샤잠이 강한 이유는 잡음을 없애서가 아니라, 살아남은 극소수 특징만으로 원곡임을
증명할 수 있는 검색 구조이기 때문입니다.

논문에 없습니다.

## 3. 대화가 놓친 것과 바로잡을 것

### 3.1 fan-out은 생존 확률을 "올리지" 않는다

대화는 "조합을 많이 만들면 살아남을 가능성이 높아진다"고 했지만, 비교 대상이 빠졌습니다.

| 방식 | 생존 단위 | p = 0.2 | p = 0.5 |
|---|---|---|---|
| 피크 하나 (해시 없음) | p | 20% | 50% |
| 쌍 해시 하나 | p² | 4% | 25% |
| 쌍 해시, anchor당 하나 이상 (F = 10) | `p·[1 − (1 − p)^F]` | 17.9% | 50.0% |
| **삼중 해시 하나 (Panako)** | p³ | **0.8%** | **12.5%** |

- anchor 자신이 살아남아야 하므로 상한은 p입니다. fan-out은 쌍으로 묶으며 잃은 몫을 되찾을 뿐입니다.
  논문도 "결국 별로 손해 보지 않는다"고 정리하고, 대가로 저장 공간 F배를 냅니다.
- **잡음에 강해지는 진짜 이유**는 두 가지가 겹친 데 있습니다. 해시 하나가 특이해서 우연 일치가 드물고,
  Δt 투표가 우연 일치를 걸러 주므로 아주 적은 생존 해시로도 판정할 수 있습니다.

### 3.2 잔향은 더하기 잡음이 아니다

우리 실패의 주원인은 [평가](evaluation.md)에 정리된 대로 홀 잔향입니다.

| 조건 (25곡, 30 s, Panako) | 식별 |
|---|---|
| 잔향만, 직접음 > 잔향 (DRR +3 dB) | 25/25 |
| 잔향만, DRR −3 dB | 13/25 |
| crowd만 0 dB / −3 dB | 18/25 / 7/25 |
| crowd 3 dB + DRR −3 dB | 2/25 |
| `crowd0_room` (100곡) | 0% |
| 배틀 영상 실측 | 2,344창 중 41창만 fingerprint로 확정 (2% 미만) |

대화의 `X = S + N` 모델로는 이것을 설명할 수 없습니다. 잔향은 `x = s * h`(컨볼루션)입니다. 아래는 Panako
파라미터를 넣고 따져 본 **가설**이며, 측정으로 확인해야 합니다.

- **피크 선택이 바뀝니다.** Panako 피크는 주파수 103 bin(약 1.2옥타브) × 시간 25프레임(8 ms × 25 = 200 ms)
  최대값 필터를 통과해야 합니다. 홀 RT60(보통 1–2 s)은 이 창보다 훨씬 깁니다. 그래서 강한 킥이나 신스의
  꼬리가 ±100 ms 안의 약한 다음 음을 눌러 피크 목록에서 지울 수 있습니다. 이건 랜덤 삭제가 아니라 **음악
  구조에 따라 체계적으로 생기는 삭제**라서 p의 IID 가정이 깨집니다.
- **주파수가 밀립니다.** 방의 전달함수에는 촘촘하고 날카로운 노치(comb filtering)가 있습니다. 논문
  스스로 단서로 단 "전달함수가 급히 변하는 곳 근처 피크는 주파수가 밀린다"는 조건에 해당합니다. Panako는
  85 bin/옥타브라 bin이 좁아서 작은 이동도 해시를 바꿉니다(`PANAKO_QUERY_RANGE = 2`가 일부를 흡수).
- **시간이 번집니다.** 온셋이 늦게 잡히거나 꼬리에서 가짜 피크가 생깁니다. Panako 해시의 시간 성분은
  Δt 비율이고, Δt는 16–264 ms(`FP_MIN/MAX_TIME_DIST` 2–33프레임)입니다. 수십 ms 번짐도 비율을 크게
  바꿉니다.
- 우리 rhythm fallback이 잔향에서 통하는 이유가 바로 이것입니다. 피크의 정확한 위치를 버리고
  150–5500 Hz 대역 온셋 포락선의 **상관**을 보기 때문입니다.

### 3.3 우리 엔진은 Panako — Shazam과 다른 점

Panako(`PANAKO` 전략)가 저장과 검색에 실제로 쓰는 해시는 `PanakoFingerprint.hash()`가 만드는 34비트
값입니다. 같은 파일의 `robustHash()`는 이 전략에서 쓰이지 않습니다. (2026-10-16 정정: 처음 판에서는
`robustHash()`를 기준으로 설명했습니다.)

| 비트 | 내용 | 잡음·잔향 민감도 |
|---|---|---|
| 0–5 | 시간 비율 `(t2−t1)/(t3−t1)` × 64 (6비트) | 템포에 불변. 시간 번짐에 민감. `PANAKO_QUERY_RANGE = 2`가 이 하위 비트를 ±2만큼 허용 |
| 6–8 | f1>f2, f2>f3, f3>f1 | 낮음 |
| **9–11** | **m1>m2, m2>m3, m3>m1 (피크 크기 순서)** | **높음(가설).** 잔향, 관중, EQ가 크기를 바꾸면 뒤집힐 수 있음. Shazam은 진폭을 일부러 버림 |
| 12–13 | (t2−t1) > (t3−t2), \|f2−f1\| > \|f3−f2\| | 중간 |
| 14–21 | f1 대략 위치 (f1 >> 5, 32 bin ≈ 0.38옥타브 단위) | 낮음 |
| 22–27, 28–33 | \|f2−f1\| >> 2, \|f3−f2\| >> 2 (4 bin ≈ 0.05옥타브 단위) | 중간. 로그 주파수 축의 차이라 피치 이동에는 불변이지만, 방의 노치로 피크가 몇 bin만 밀려도 바뀜 |

- **세 점이 모두 살아남아야 합니다.** 같은 p에서 해시 생존이 p³입니다(3.1 표).
- 대신 속도와 피치를 바꿔도 같은 해시가 나옵니다. 우리 PoC에서 속도 ±3% + crowd 6 dB가 82–85%인 것은
  이 덕분입니다.
- **우리 crowd-only 성적이 Shazam 논문보다 약해 보입니다.** 잡음 종류, SNR 정의, DB 크기가 달라 직접
  비교는 못 합니다. 그래도 우리는 30 s 클립인데 crowd 0 dB에서 72%(18/25), 3 dB에서 83%입니다. 논문은
  15 s, 펍 소음 0 dB에서 약 97%입니다(발표 그래프 판독치이고, 본문 기준으로는 −9 dB에서 이미 50%). 이 차이는 triplet(p³)과 크기 비트 가설과 어긋나지 않습니다.
  **검증 필요.**

## 4. 이 검토가 프로젝트에 주는 시사점

1. **"녹음 길이"는 가장 싼 지렛대입니다.** 논문에서 −6 dB 조건은 5 s 22%에서 15 s 84%로 올랐습니다.
   우리도 rhythm에서 같은 경향을 이미 봤습니다(조기 종료 보정). Panako 쪽에서는 아직 측정하지 않았습니다.
2. **임계값은 고정값이 아니라 오탐률로 정하는 것입니다.** 우리에게는 null 데이터가 있습니다. 배틀에서
   아무것도 못 찾은 1,618창과 라이브러리에 없는 곡 356창입니다.
3. **Panako의 속도 불변성은 잡음 강건성과 맞바꾼 것입니다.** 배틀 실패 사례는 모두 속도 1.000이었습니다.
   그래서 "속도 불변이 아닌 대신 생존율이 높은" 2점 해시를 Panako 실패 후 2차로 두는 구성은 따져 볼 만합니다.
   속도가 다른 경우는 rhythm wide가 이미 맡고 있습니다.
4. **잔향은 피크 기반 해시 계열 전체의 한계입니다.** E1–E6으로 얼마나 올라가든, 근본 해결 후보는 설계안
   A/B(학습된 임베딩)입니다. E 실험은 그 전에 기준선을 세우고 값싼 개선을 거두는 단계입니다.

## 5. 개선 후보 (실험 계획)

> **실험 결과는 [fp-experiments-e1-e6.md](fp-experiments-e1-e6.md)에 있습니다** (2026-10-16). 가장 큰 개선은 E5(2점 해시)이고, E3도 효과가 있었습니다. E6 Demucs는 실측 배틀에서 손해였습니다.

공통 평가 세트:
- 합성: `poc/testset`의 `crowd0_room`, crowd 0/−3 dB, DRR ±3 dB, 속도 ±3%
- 실측: `realtest/battle100` 창(2,344), 그중 nothing-found 1,618창, 라이브러리에 없는 곡 356창
- 기준: 식별률, **오확정 0건 유지**, Lambda 지연 시간, fingerprint DB 크기

| ID | 가설 | 방법 | 비용 | 위험 |
|---|---|---|---|---|
| **E1** 오탐률 기반 Panako 임계값 | 고정 `score ≥ 10`이 너무 보수적이어서 약한 정답을 버리고 있을 수 있음 | 쿼리 시 `PANAKO_MIN_HITS_UNFILTERED/FILTERED`, `PANAKO_MIN_MATCH_DURATION`을 낮춰 sub-threshold 점수까지 받음. null 창들로 "최고 오답 점수" 분포를 만들고 0.1% 오탐에 맞는 임계값을 정함 (논문 2.3.1절) | 낮음. DB 재빌드 없음 | [평가](evaluation.md)상 배틀은 "약한 후보조차 없음"이라 상승폭이 작을 수 있음. **먼저 측정** |
| **E2** 녹음 길이 / 창 누적 | 길이가 늘면 정렬 해시가 쌓여 임계값을 넘음 (논문 Fig. 4) | battle100 오디오로 같은 위치를 30 s와 60 s로 Panako 쿼리해 비교. 효과가 있으면 "Panako 실패 + rhythm 약함"일 때만 녹음을 연장하거나, 연속 창의 hit를 Δt 정렬해 합산 | 낮음 (측정). 연장은 UX 비용 | 잔향 열화는 길이로 안 풀릴 수 있음 |
| **E3** 크기 순서 비트 제거 | 비트 9–11이 잡음·잔향에서 뒤집혀 해시를 깸 | `hash()`에서 m 비트를 0으로 패치. 작은 DB(`poc/test_db`)로 재빌드해 합성 조건 비교 | 중간. 패치 + 소규모 재빌드. 본 DB 반영 시 43분 재빌드 | 엔트로피 3비트 감소 → 충돌과 오탐 증가. E1 방식으로 오탐 확인 |
| **E4** 피크 밀도·fan-out 조정 | 기본값은 깨끗한 음원 기준. 휴대폰·홀 조건에는 더 촘촘하게 (논문 2.2절) | `PANAKO_FREQ_MAX_FILTER_SIZE`(103), `PANAKO_TIME_MAX_FILTER_SIZE`(25), `PANAKO_FP_MAX_TIME_DIST`(33)를 격자로 탐색. 작은 DB에서 비교 | 중간–높음. print 수와 DB 크기가 늘어 Lambda 이미지와 메모리에 영향 | 잡음 피크도 늘어남. Δt 투표가 걸러 줄지 확인 |
| **E5** 2점 해시 2차 엔진 | 속도 1.000인 배틀에서는 p²가 p³보다 유리함 | audfprint(파이썬 pair landmark, density/fanout 조절 가능)나 numpy 자체 구현으로 별도 인덱스를 만듦. Panako 실패 시에만 실행. `crowd0_room`과 battle100으로 비교 | 높음. 별도 인덱스, 서버 통합 | 속도 불변 아님(±1% 넘으면 실패). 잔향 문제는 그대로일 수 있음 |
| **E6** 전처리 A/B | 관중과 MC를 빼면 피크 생존율이 오름 | ① Demucs로 vocals 제거 (MC, 함성 일부) ② WPE 계열 잔향 제거. 각각 원본 혼합 대 전처리 후의 Top-1, 오확정, 시간을 비교 (대화의 추천 그대로) | 높음. Lambda CPU에서 Demucs는 수 초 이상 | 대화의 경고대로 드럼 어택과 배음을 손상시킬 수 있음. Demucs는 음악에 붙은 잔향을 지우지 않음 |

권장 순서는 다음과 같습니다.
1. **E1, E2**: 측정만. 재빌드 없음.
2. **E3, E4**: 작은 DB.
3. 결과에 따라 **E5**.
4. **E6**는 마지막.

설계안 A의 Phase 0(사전학습 NMFP 영점 평가)는 독립적이라 병행할 수 있습니다. E 실험 결과는 A/B 평가의
비교 기준선으로도 씁니다.
